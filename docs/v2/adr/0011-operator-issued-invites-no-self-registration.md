# ADR 0011: New users join via operator-issued invite tokens

**Status**: Accepted
**Date**: 2026-05-10
**Decision-makers**: phall
**Related**: [ADR-0005](0005-multi-user-data-model-from-day-one.md),
[ADR-0007](0007-self-hosted-only-no-saas.md),
[ADR-0010](0010-one-daemon-many-users.md),
[design/multi-user.md](../design/multi-user.md)

## Context

A homelab daemon serving friends-and-family ([ADR-0007](0007-self-hosted-only-no-saas.md))
has a small, trusted user set. Self-registration (email + password
+ verification email) is wildly more machinery than the use case
needs and introduces failure modes (email deliverability, abuse
prevention, captcha-equivalent) we shouldn't be running.

Trust is established out-of-band: phall texts james "want me to add
you?" and james says yes. The system just has to ratify that
exchange.

## Decision

User onboarding is a two-step, operator-driven flow:

1. **Operator creates the user**, on the box, in the operator's
   shell:
   ```
   $ resy-snipe user invite james@example.com --role=user
   invite link: https://snipe.phall.example/invite/8xK3aZ2qR…
   expires: 2026-05-17 23:59 UTC
   ```
2. **Invitee opens the link** (in browser or via Claude / a CLI
   `resy-snipe accept-invite <link>`), sets a password, gets a
   bearer token. The invite is single-use and short-lived.

There is no signup form. There is no "register" endpoint. The
operator is the gatekeeper.

## Consequences

**Positive**
- Zero abuse surface: there is no path for a stranger to create an
  account.
- No email infrastructure required. The invite link is text the
  operator sends out-of-band (iMessage, Signal, in person).
- Audit-friendly: every user has an inviter row recorded.
- Roles (admin / user / read-only) are set at invite time and
  immutable thereafter (admin can rotate via re-invite).

**Negative**
- Operator must be hands-on for onboarding. Not a goal to "scale" —
  see [ADR-0007](0007-self-hosted-only-no-saas.md).
- Lost-password flow requires operator action: `resy-snipe user
  reset james@…` issues a new invite, the friend sets a new password.
  Friends-and-family scale, this is fine.

**Neutral**
- The MCP transport ([ADR-0004](0004-mcp-as-peer-front-end.md))
  authenticates with the same bearer tokens. James's Claude Code
  attaches with james's token, period.

## Alternatives considered

1. **Self-registration with email verification.** *Rejected:*
   email infra (deliverability, SPF/DKIM, abuse) is a project of its
   own; not worth it for ≤10 users.
2. **OAuth / Google Sign-In.** *Rejected:* couples the daemon to a
   third-party identity provider, adds outbound dependency, and
   doesn't actually limit who can sign up unless we maintain an
   allowlist (which is just operator-issued invites with extra steps).
3. **Pre-shared passwords (operator emails the friend a password).**
   *Rejected:* passwords-in-email is the worst of both worlds.
   Invite-link-then-set-password is strictly better.
4. **No accounts; tokens-only, generated by operator.** *Rejected:*
   loses password-based reauth and makes the friend's own password
   manager less useful. A token that never expires is itself an
   ongoing risk.

## Notes

Invite tokens are 256 bits of `crypto/rand` base64url-encoded,
single-use, expire in 7 days by default (configurable). Stored in
`invites` table:

```sql
CREATE TABLE invites (
  token_hash   BLOB PRIMARY KEY,         -- SHA-256 of the secret
  email        TEXT NOT NULL,
  role         TEXT NOT NULL,
  invited_by   TEXT NOT NULL REFERENCES users(id),
  created_at   INTEGER NOT NULL,
  expires_at   INTEGER NOT NULL,
  consumed_at  INTEGER                   -- nullable; set on first use
);
```

We store the token hash, not the token itself, so an operator dumping
the DB can't reuse outstanding invites.

The invite-acceptance page is the daemon's only unauthenticated
endpoint other than `/healthz`. It rate-limits aggressively
(per-IP + per-token-prefix) to defeat brute-force on the token
namespace.

See [design/multi-user.md](../design/multi-user.md) for the user
schema and bearer-token format.
